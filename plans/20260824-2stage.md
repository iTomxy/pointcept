# Two-stage Pipeline

Both stage are segmentation on the same dataset:
- stage-1 is FG-BG binary segmentation: {
    0: background, other voxels (including other bone voxels),
    1: foreground, rib voxels
}
- stage-2 is multi-class rib segmentation/labeling/numbering based on the predicted FG voxels from stage-1: {
    0: background
    1-24: rib1 - rib24
}

1. Train the stage-1 fg-bg segmentation model.
This needs to binarise the label in the data transform.
Reference:
    - `~/codes/tmp.ptcloud/log/ribsegv2/semseg-dgcnn-bin-opt/config.json`
    - `BinarizeLabel` in `~/codes/tmp.ptcloud/datasets/transform.py`.

2. Predict the whole dataset (train/val/test) with the trained stage-1 model.

3. Reconstruct the point-wise binary prediction to 3d volumes with
`recon_3d_bin_pred` in [pointcept/datasets/ribsegv2/preproc.py](../pointcept/datasets/ribsegv2/preproc.py).
    - Save in the `recon-3d-binpred/` sub-folder under the stage-1 log path.

4. Re-preprocess with `preprocess_ptcloud` in [pointcept/datasets/ribsegv2/preproc.py](../pointcept/datasets/ribsegv2/preproc.py)
together with the reconstructed 3d binary prediction volumes.
    - Save in the `pt_preproc-binpred` sub-folder under the stage-1 log path.
    Do not overwrite the original `pt_preproc/` folder.

5. Train the stage-2 multi-class segmentation model with `pt_preproc-binpred`.

6. Test with combined prediction of stage-1 and stage-2.
    - Combine: replace the stage-1 FG prediction with stage-2 prediction.
    One detail: stage-2 testing prediction should cover all voxels, i.e. no `drop_last`.
    Otherwise the prediction of those dropped voxels are undefined.

Verified as **needing no change**:

- **The plan's `drop_last` caveat is already satisfied.** `Ribsegv2VolumeTester`
  runs one whole volume per item (`batch_size=1`, `collate_fn` returns
  `batch[0]`) and scatters the grid prediction back over every original point
  through `inverse`, so coverage is complete by construction. Its
  `DistributedSampler` pads the volume list, but records are keyed by volume id
  and deduped, so the padding cannot double-count either.
- **Losses.** `CrossEntropyLoss` and `LovaszLoss(mode="multiclass")` are
  class-count agnostic.
- **`NormalizeCoord(radius=259.16)`.** That figure was measured over the rib
  classes alone, so it is already the right scale for a foreground-only cloud;
  the centroid is per-sample and recentres on its own.
- **Cached intensity statistics.** `intensity_{min,max,mean,std}` are
  whole-volume figures computed before thresholding, so the stage-2 cache
  carries stage-1's values unchanged and `WindowIntensity` is unaffected.

**Volume accounting.** `IGNORE_VOLUMES` drops 11 ids, so the splits are
419 + 73 + 157 = **649** volumes against the 657 `.npz` in
`data/ribsegv2/pt_preproc` (-> `/data/tliang/ribseg/pt_preproc`, 3.0 GB).
`preprocess_ptcloud` skips a volume whose sieve is absent, so the stage-2 cache
should legitimately hold 649 -- **assert that count after step 4**, since
nothing downstream would notice a half-built cache. Budget ~3 GB for
`pt_preproc-binpred` (stage 2 is a strict subset) plus the reconstructed
`.nii.gz` sieves (~0.25 GB at int8).

## A1. `BinarizeLabel` -- exists, but its position is load-bearing

Already registered at
[transform.py:283](../pointcept/datasets/transform.py#L283); `coi -> 1`,
everything else `-> 0`, acting on `segment` (`ReadNpz` renames the cached
`label` to `segment`). No new code. **Two ordering constraints, both live:**

1. **After `RandomTruncateRibPoint`.** That transform picks whole ribs out by
   class id and returns early when `n_p < 2`
   ([transform.py:1980](../pointcept/datasets/transform.py#L1980)). Binarising
   first leaves one foreground class, so `n_p == 1` and the augmentation
   silently stops firing -- no error, just a stage-1 run missing the +2.96 pt
   lever the tuning identified.
2. **Before the `Copy` to `origin_segment`.** `Ribsegv2VolumeTester` scores the
   prediction against `origin_segment`, not the transformed `segment`. After
   the copy, stage 1 would compare 2 predicted classes against 25 target ones,
   and nothing would raise.

The tuned train pipeline puts `RandomTruncateRibPoint` right after
`TypeCast`/`Update` and the `Copy` late in the test branch, so a single position
-- immediately after the `CTIntensityVariation`/`WindowIntensity` block --
satisfies both.

## A2. Stage-1 class count -- config only

`model.num_classes=2` and `data.num_classes=2`, plus `data.names=("background", "rib")`.
`backbone.in_channels` stays 1 (`whu0`). `test.rib_metrics` auto-disables itself
below 25 classes, and `SemSegEvaluator` already excludes `bg_classes=[0]` from
every macro average, so a 2-class run reports foreground IoU/Dice directly.

## A3. Prediction export -- already implemented

`Ribsegv2VolumeTester(save_pred=True)` writes
`{save_path}/result/{vid}.npz` holding `pred`, `label` and `voxel_index` at
**original, pre-GridSample resolution and in original order**
([test.py:1455](../pointcept/engines/test.py#L1455)) -- exactly what
`recon_3d_bin_pred` consumes. The sibling repo needed a writer plus a partition
un-permute here; PTv3 needs neither, because `inverse` already returns original
point order.

## A4. Predicting all three splits -- config only

`data.test.split="all"` (`SPLITS["all"]`, 649 volumes). Stage 2 needs a sieve for
train/val/test alike, not just the test split. Keep `add_trainval_incomplete`
and `test_all_incomplete` off.

## A5. Empty stage-2 clouds -- done

`preprocess_ptcloud(min_points=...)` / `--min-points`. If stage 1 predicts no
foreground for a volume, the guard skips it and reports every such volume at the
end, instead of writing a 0-point `.npz` that fails later inside a dataloader
worker where `GridSample` and `NormalizeCoord` reject it far from the cause.

## A6. Stage-2 cache wiring -- done, needs the config

`Ribsegv2Dataset(cache_root=...)` and `Ribsegv2VolumeDataset(cache_root=...)`
(added 2026-08-24) point the `.npz` lookup at
`<stage-1 log>/pt_preproc-binpred` instead of `{data_root}/pt_preproc`.
`num_classes` stays 25.

## A7. Combined evaluation -- the one real gap

Nothing merges two runs. Needed for step 6, as `tools/combine_2stage.py`.

**Combination rule**, over the **stage-1 point set**: start at 0, and for each
point stage 1 called foreground take stage 2's label. Points that step 3's
`remove_statistical_outlier` dropped have no stage-2 label and stay 0 -- report
that count rather than hiding it. Both caches index the same LPS grid, so the
two point sets are matched on `voxel_index` triples, not by position.

**Score over the stage-1 point set**, i.e. every HU > 200 voxel in `pt_preproc`
-- the same denominator the 1-stage runs report on, so the numbers drop straight
into the [Performance Table](#performance-table). Scoring only stage 2's smaller
set would quietly excuse every voxel stage 1 lost.

**25-class ground truth comes from `data/ribsegv2/pt_preproc/{vid}.npz`**, not
from either prediction dump: stage 1's `label` was binarised by A1, and stage
2's covers only its subset.

## A8. Stage-1 checkpoint selection -- F2, not mIoU

Stage 2 only ever sees the foreground stage 1 kept, so a rib voxel stage 1 drops
is gone for good, while a false positive is still correctable downstream. mIoU
weighs the two equally -- right for a one-stage model, wrong here.

Plain recall is the wrong fix: it is maximised by calling everything foreground.
F-beta with beta=2 weighs recall four times as heavily but still penalises
over-prediction.

**Measured 2026-08-24, and it corrects the sibling plan's figure.** The F2 of an
all-foreground predictor is `5p / (4p + 1)` in the foreground fraction `p`, so
it is not a fixed floor. The sibling plan quotes 0.34 against a balanced model's
0.50, which holds at `p ~ 0.09`; on RibSegv2 `p` is 0.13-0.39 per volume
(mean 0.216 over val, from `grid-stats-val-3.0mm.json`), so the degenerate model
actually scores **0.43-0.76 -- above** the balanced model's 0.50. Do not carry
that number across.

The criterion is still sound, for a different reason than the sibling gives: the
gap to a *useful* gate is what matters, and precision 0.90 / recall 0.95 scores
0.94, far above the degenerate 0.58 at the mean ratio. So F2 ranks real models
correctly and will not crown an all-foreground one -- but its absolute value is
not comparable across datasets, and `Currently Best` in the stage-1 log should
not be read as a quality score.

[hooks/evaluator.py:246](../pointcept/engines/hooks/evaluator.py#L246) hardcodes
`current_metric_value = m_iou`. It already has everything needed per class:
`TP = intersection`, `FN = target - intersection`, `FP = union - target`. Make
the selection metric configurable, defaulting to `mIoU` so every existing config
is untouched, and log F2 alongside so all runs report it.

## A9. The 2-stage configs must overlay the **tuned** base

[semseg-pt_v3m1_0_base-bin.py](../configs/ribsegv2/semseg-pt_v3m1_0_base-bin.py)
already does stage 1, but it predates the sequential tuning and restates a
pipeline that no longer matches
[semseg-pt_v3m1_0_base.py](../configs/ribsegv2/semseg-pt_v3m1_0_base.py):
it uses `strength` rather than `whu0`, `max_points=250000` rather than 200000,
`lr=0.006` with no `param_dicts`, and a `RandomApply` over `RandomDropRibPoint`
+ `RandomTruncateRibPoint` at `max_drop_depth=7, p=0.5` -- an augmentation set
the tuning **rejected** (`RandomDropRibPoint` measured -0.58). Using it would
make stage-1 numbers incomparable with the tuned 1-stage baseline. The new
configs overlay the tuned base instead; `-bin.py` is superseded.

This is a drift hazard, not a one-off: Pointcept's `_base_` merges dicts but
**replaces lists wholesale**, and the base deletes `build_pipeline` from its own
namespace, so an overlay cannot reuse the builder and has to restate it -- which
is exactly how `-bin.py` went stale. The repo convention (see
[seq-tune/](../configs/ribsegv2/seq-tune/)) is to restate; keep the delta from
the base to the documented minimum and re-check it whenever the base changes.

## A10. Reuse the tester's scorer from a script

`Ribsegv2VolumeTester.eval_volume` / `.reduce`
([test.py:1523](../pointcept/engines/test.py#L1523)) produce exactly the columns
the [Performance Table](#performance-table) wants, but they are instance methods
on a class whose `__init__` builds a CUDA model and a dataloader. A7 needs them
without either. Extract both bodies into module-level functions parameterised by
`(num_classes, bg_class, metrics, rib_metrics)` and have the methods delegate,
so the combined numbers come from the same code path as the per-stage ones
rather than a second implementation that can disagree.
